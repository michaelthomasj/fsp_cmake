Cortex-M, TrustZone and TF-M on Renesas RA

From an empty mental model to being able to read a fault dump from an isolation-level-3 TF-M build on an RA6M5, explain it, and decide what to change. Every claim from Part 1 onward is tied to a file, a line, or a measurement in this repository.

Who this is for

  • You can read and write C, and have read a microcontroller datasheet.
  • You have not met privilege levels, an MPU, TrustZone, or a secure partition manager.
  • You will be asked to work on, or port, the TF-M port in this repository.

How to read it

  • In order. Each part uses the vocabulary of the previous one. Part 0 is a conventional primer and is safe to skim if you already know Cortex-M exception handling.
  • Follow the "Later:" boxes. Part 0 points forward to the place where each idea gets tested on real hardware. They are where the textbook version stops being sufficient.
  • Answer the questions at the end of each page before moving on. Answers are folded under each question; every one is answerable from that page.

Four kinds of claim, and why the tags matter

A statement about this system is one of four different things. Mixing them up is the commonest way to draw a wrong conclusion, so every substantive claim carries a tag:

TagMeansExampleCan it change?
Armv8-MThe Arm architecture requires it. True on every Cortex-M33/M85. Unprivileged code cannot write the NVIC.No.
TF-MTrusted Firmware-M chose it. True on every TF-M platform, until TF-M changes. Above isolation 1, an Application-RoT FLIH handler runs in Thread mode.Upstream, by patch.
RARenesas silicon or the FSP does it. True on RA parts. An interrupt's security state lives in both NVIC->ITNS and ICUSARG.Per device / FSP release.
This portThis repository chose it. The port marks interrupts Secure only through the secure e2 project, never with NVIC_ClearTargetState().Here.

Most worked examples use the RA6M5, because it was the first part measured at isolation 2 and 3 (D113, D114, GNUARM) and the debugging story happened there. Citation conventions

  • DECISIONS.md D113 — an entry in this repository's append-only decision log, DECISIONS.md. Entries are never edited; a later entry supersedes an earlier one.
  • Every link to a repository document opens an HTML rendering of it under ref/, regenerated from the Markdown on each commit. A decision number such as D113 links straight to its entry; "DESIGN.md §8.4" links to that section.
  • tfm_hal_isolation_v8m.c:410 — a file in the TF-M checkout at C:\Users\Michael\Documents\GitHub\trusted-firmware-m, under platform/ext/common/ unless a fuller path is given. Line numbers are from TF-M commit b1b9078ff (2026-10-21). Citations into upstream files the port does not modify drift only on a TF-M uprev; citations into platform/ext/target/renesas/ can move with any port commit. An FSP update cannot move any TF-M citation.
  • Port files are under trusted-firmware-m/platform/ext/target/renesas/<part>/ and cited as ra6m5/tfm_timer0_irq.c:86.
  • FSP files are cited from the generated e2 project, e.g. ra6m5_gcc_secure/ra/fsp/src/bsp/mcu/all/bsp_security.c:399.

The record corrects itself, and that is part of the material. Several statements in this repository were found not to match the source and have since been corrected by later log entries. The course keeps them as worked examples, in boxes like this one where they come up:

  • D114 said TFM_PXN_ENABLE never becomes a compile definition. It does (platform/CMakeLists.txt:126, since 2021). Corrected by D115 and D117 — Part 3.
  • Three RA6 ports' target_cfg.c said the part has no IDAU and attributes via the SAU. The reverse is true. Fixed in TF-M b1b9078ff, D117 — Part 2.
  • D113 said TF-M runs FLIH handlers in Thread mode. Only for an Application-RoT partition above isolation 1. Corrected by D117 — Part 3.
  • D116 closed the L1+IPC boot-order question "by irrelevance, not by analysis". It had an answer. Corrected by D117 — Part 1.
  • D113–D117, and the first editions of this course, called the missing TFM_ISOLATION_LEVEL an upstream defect on every platform. It is not: every upstream platform compiles the shared HAL in tfm_spm, which always receives the macro; the RA ports compiled it in platform_s, which does not. Measured on an519; corrected by D120, which withdraws upstream item 15, and fixed by D121, which moves the HAL to tfm_spm (ra6m4 untouched) — Part 3.
  • D121 said the moved code left the PSA RoT code region. It did not: both linker sections lie inside it, and the region grew by 32 bytes. Corrected by D125 — Part 3.
  • D115 said only L1+IPC could hit the hook link error, because SFN has no call site. SFN does call it. Corrected by D126 — Part 3.

D117's own summary of the pattern: a true observation written down as a more general statement than the evidence supported.
