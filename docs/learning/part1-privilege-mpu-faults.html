Part 1 — Privilege, the MPU, and faults

How the core decides whether a piece of code may touch a piece of memory, what happens when it may not, and how to read the evidence afterwards. From here on, examples are measurements from this repository.

1.1 Two modes, two privilege levels

Armv8-M At any moment the core is in one of two modes:

  • Handler mode while running an exception handler. Always privileged. Always uses MSP.
  • Thread mode otherwise. Privileged or unprivileged according to CONTROL.nPRIV; uses MSP or PSP according to CONTROL.SPSEL.

Privileged code may execute every instruction, write every special register, and reach the PPB. Unprivileged code cannot write CONTROL, cannot change PRIMASK/BASEPRI/FAULTMASK (writes are ignored), cannot reach the PPB (BusFault), and is subject to the MPU's unprivileged permissions.

"Handler mode is privileged" does not mean "interrupt handlers are privileged". The first is architecture. The second depends on software. TF-M, for an Application-RoT partition at isolation 2 and 3, takes an interrupt in Handler mode and then deliberately runs the owning partition's handler in Thread mode, at the partition's privilege; on this port that made an ICU register write fault. Mechanism in Part 3 §3.6.

It runs from the SPM, which is privileged, so the write is legal; privileged is computed in the isolation HAL (Part 3 §3.7).

1.3 MSP, PSP, and stack limits

  • Armv8-M MSP is used by Handler mode and by Thread mode when SPSEL = 0. PSP is used by Thread mode when SPSEL = 1.
  • Armv8-M MSPLIM/PSPLIM: an instruction that would move SP below the limit raises UsageFault STKOF (UFSR bit 4) and the access does not happen.
  • TF-M The SPM boots on MSP. Each IPC-model partition is a thread with its own stack on PSP; the stack and its limit are swapped by PendSV (§1.7). The reload is explicit:
        "   ldr     r3, [r1]                            \n" /* Load sp_limit */
        "   msr     psp, r2                             \n"
        "   msr     psplim, r3                          \n"

secure_fw/spm/core/arch/tfm_arch_v8m_main.c:145-147 (inside PendSV_Handler)

  • TF-M Entering the SPM from a thread saves the caller's PSPLIM (tfm_arch_v8m_main.c:60), clears it, switches SP to the SPM stack, then sets the SPM stack's own limit (:66-76), so no transient SP value trips a limit. The caller's limit is restored on the way out (:86-89).
  • This port The MSP stack size must equal BSP_CFG_STACK_MAIN_BYTES + STACKSEAL_SIZE; S_MSP_STACK_SIZE is 0x1008 on RA6M5 (ra6m5/region_defs.h:255) and the equality is asserted at build time (CONFIGURATION.md §7).

1.4 The MPU

Armv8-M The Memory Protection Unit (PMSAv8) checks every data access and instruction fetch against a small table of regions. A region is a base, a limit, permissions and a memory-type index. The MPU is per security state; this section describes the Secure MPU, which is the one TF-M programs.

Registers

RegisterAddressUse
MPU_TYPE0xE000ED90DREGION[15:8] = number of regions implemented. Read it; do not assume it.
MPU_CTRL0xE000ED94ENABLE bit 0, HFNMIENA bit 1, PRIVDEFENA bit 2
MPU_RNR0xE000ED98selects which region RBAR/RLAR refer to
MPU_RBAR0xE000ED9CBASE[31:5], SH[4:3], AP[2:1], XN[0]
MPU_RLAR0xE000EDA0LIMIT[31:5], PXN[4] (Armv8.1-M only), AttrIndx[3:1], EN[0]
MPU_MAIR0/10xE000EDC0/C4eight 8-bit memory-attribute encodings, selected by AttrIndx

Bit positions: core_cm33.h:1485-1521; MPU_BASE = SCS_BASE + 0x0D90, core_cm33.h:2059.

Encoding rules, and why they exist

  • 32-byte granularity. Base and limit are stored in bits [31:5]. The base's low five bits are taken as 00000, the limit's as 11111. A region therefore starts on a 32-byte boundary and its last byte is at …1F. Unlike Armv7-M, sizes need not be powers of two — which is what lets TF-M fit regions tightly around linker sections.
  • AP, from ARM_MPU_AP_(RO, NP) = (RO << 1) | NP (armv8m_mpu.h:140): 00 RW privileged only, 01 RW any, 10 RO privileged only, 11 RO any.
  • Overlaps fault. If an address hits more than one enabled region, the access faults. There is no "highest region number wins" rule as in Armv7-M.
  • PRIVDEFENA gives privileged code the architectural default map for any address no region covers. Unprivileged code gets no default: an unprivileged access that hits no region faults. In effect the background map is a free, lowest-priority "privileged-only, everything" region.
  • HFNMIENA keeps the MPU enabled while running HardFault and NMI handlers.
  • The PPB is outside the MPU's reach. PPB accesses always use the default map, which makes them privileged-only. No region, however configured, grants unprivileged code access to 0xE0000000–0xE00FFFFF.

1.5 Exceptions in depth: what the hardware stacks

Armv8-M On exception entry the hardware pushes a state context onto the stack that was in use (MSP or PSP, Secure or Non-secure). Two optional extensions can be added:

TF-M TF-M's own context switch reads the DCRS bit to know whether the hardware already saved R4–R11:

        "   ands    r3, lr, #"M2S(EXC_RETURN_DCRS)"     \n" /* Check DCRS */
        "   itt     ne                                  \n" /* Skip saving callee */
        "   stmdbne r2!, {r4-r11}                       \n" /* Save callee */
        "   subne   r2, #8                              \n" /* SP offset for
                                                             * reserved additional state context,
                                                             * integrity signature
                                                             */

tfm_arch_v8m_main.c:122-128

The subne r2, #8 makes a software-saved context the same shape as a hardware-saved one, so either can be restored the same way.

The Secure/Non-secure stack pairs

Armv8-M With the Security Extension there are four stack pointers — MSP_S, PSP_S, MSP_NS, PSP_NS — and four limits. Which one the hardware stacks to is decided by the state being left (S bit) and the mode and SPSEL of that state. Which one the handler runs on is the MSP of the state the exception targets (ES bit). So a non-secure interrupt arriving while a TF-M partition runs stacks onto PSP_S, then runs on MSP_NS.

TF-M TF-M seals the top of the secure MSP with a known pattern (__TZ_set_STACKSEAL_S, ra6m5/startup_ra6m5.c:175-177) so that a forged exception return cannot land on it.

1.7 SVC and PendSV

Two exceptions exist for software rather than hardware. They do different jobs.

SVC in TF-M

TF-M The handler is a short assembly shim that gathers MSP, PSP and EXC_RETURN and calls spm_svc_handler() in C (tfm_arch_v8m_main.c:156-166, secure_fw/spm/core/tfm_svcalls.c:250). The SVC number in the instruction selects the request. Two examples you will meet:

  • An unprivileged partition calling a PSA API at isolation 2/3 (psa_interface_svc.c). The SVC handler switches to privileged Thread mode to run the SPM function, rather than running it in Handler mode (prepare_to_thread_mode_spm, tfm_svcalls.c:291-297).
  • TFM_SVC_PREPARE_DEPRIV_FLIH, used to drop into an unprivileged interrupt handler (tfm_svcalls.c:214-220; Part 3 §3.6).

PendSV in TF-M: how a context switch is requested

To request a switch TF-M's arch_attempt_schedule() stores PENDSVSET to ICSR at 0xE000ED04 (secure_fw/spm/core/arch/tfm_arch.c:80-101) unless the scheduler is locked. ICSR is in the PPB, so the store is legal only from privileged code; keep that in mind for §1.9.

…and how it is performed

PendSV_Handler (tfm_arch_v8m_main.c:99-153) calls ipc_schedule() to choose the next thread and switch isolation boundary, then saves R4–R11 (and S16–S31 with FP) to the outgoing thread's PSP, stores {PSP, EXC_RETURN} in its context, loads the incoming thread's, restores its PSP and PSPLIM, and returns. The returning EXC_RETURN belongs to the incoming thread, so the exception return lands in it.

Why defer to PendSV rather than switch inside the SVC handler? Because PendSV is the lowest-priority secure exception, it runs only after every more urgent handler — including any interrupt that arrived meanwhile — has finished. The switch therefore never happens underneath another handler's feet.

1.8 Fault registers

Armv8-M Four configurable fault exceptions report cause through status registers in the SCB. MemManage, BusFault, UsageFault and SecureFault must each be enabled in SHCSR, or they escalate to HardFault. This port enables all four in enable_fault_handlers() (ra6m5/target_cfg.c:110-121).

CFSR, decomposed

CFSR at 0xE000ED28 is three registers in one word:

Byte(s)Sub-registerBits that matter here
[7:0]MMFSR — MemManage bit0 IACCVIOL instruction fetch violation · bit1 DACCVIOL data access violation · bit3 MUNSTKERR · bit4 MSTKERR · bit5 MLSPERR · bit7 MMARVALID — MMFAR holds the address
[15:8]BFSR — BusFault bit0 IBUSERR · bit1 PRECISERR (address known) · bit2 IMPRECISERR (address lost; write buffer) · bit3 UNSTKERR · bit4 STKERR · bit5 LSPERR · bit7 BFARVALID
[31:16]UFSR — UsageFault bit0 UNDEFINSTR · bit1 INVSTATE · bit2 INVPC · bit3 NOCP · bit4 STKOF · bit8 UNALIGNED · bit9 DIVBYZERO

When software prints "BFSR 0x82" it means the byte at CFSR[15:8], not the whole word.

Address validity rules

  • MMFAR (0xE000ED34) is meaningful only if MMARVALID is set. An instruction-fetch violation (IACCVIOL) never sets it: the faulting address is the stacked PC.
  • BFAR (0xE000ED38) is meaningful only if BFARVALID. An imprecise BusFault never sets it — the write that failed retired several instructions ago.
  • MMFAR and BFAR may share storage in an implementation; read the valid bit, then the address, then clear the status.

HardFault and HFSR.FORCED

HFSR at 0xE000ED2C: bit 1 VECTTBL (vector fetch failed), bit 30 FORCED, bit 31 DEBUGEVT. FORCED means a configurable fault or an SVC escalated: it was disabled in SHCSR, or masked, or the core was already running at a priority the fault could not preempt. The original cause is then in CFSR — usually.

FORCED with every CFSR, BFSR, MMFSR, UFSR and SFSR bit clear is the signature of a masked SVC. An SVC executed with PRIMASK set cannot be taken and escalates; it is not a fault, so no fault status bit records it. On this port the trigger was a log call during ITS initialisation, made before interrupts were re-enabled; tfm_hal_platform_init() now enables them.

SecureFault

SFSR at 0xE000EDE4, SFAR at 0xE000EDE8. Bit 0 INVEP (invalid entry point) is the one this port has met: non-secure code branched into Secure memory somewhere other than an SG in a non-secure-callable region. Covered in Part 2 §2.3.

1.9 Reading real dumps

Every row happened on this port. Read each as: which sub-register, is the address valid, what lives there, and at which privilege the code ran.

The MemManage rows share a pattern: the same status byte, 0x82, for four different causes. The status tells you how the access failed; only the address and the region table tell you why. Rows 1–2 differ from rows 3–4 in whether a region existed: a privileged region exists but excludes the caller, versus no region exists at all.

Worked case: L1 + IPC, BFAR 0xE000ED04

Isolation 1 with the IPC backend HardFaulted with a precise BusFault at BFAR 0xE000ED04, on the PendSV store in arch_attempt_schedule. Reason it through:

  1. 0xE000ED04 is ICSR; the store is in tfm_arch.c:89-91.
  2. A precise BusFault on a PPB store, rather than a MemManage fault, is what an unprivileged PPB access produces (§1.4). At isolation 1 the MPU is not enabled, so privilege is the only thing that can refuse this store.
  3. At isolation 1 the SPM gives every partition the Thread-mode call ABI, which runs SPM code at the caller's privilege (backend_ipc.c:169-170). The SPM assumes every partition is privileged at level 1 — and backend_ipc.o was compiled with -DTFM_ISOLATION_LEVEL=1 (D117, from the generated compile lines).
  4. But the isolation HAL, compiled in platform_s, did not see the macro. It took the #else arm and set privileged = IS_PSA_ROT() (tfm_hal_isolation_v8m.c:410-414), so Application-RoT partitions were de-privileged.
  5. So the first psa_* call from an ARoT partition ran SPM code unprivileged, and the SPM's own ICSR store faulted. At isolation 2 the SPM instead hands such partitions the SVC ABI, so the SPM always runs privileged and execution survives into a test body — which is why L1+IPC died earlier in boot than L2.

The two halves of the firmware acted on different values of the same macro. That is the sharpest statement of the defect in Part 3 §3.8.

Check yourself

  1. A dump shows MMFSR 0x01 and an MMFAR value. Should you use the MMFAR value?
    AnswerNo. 0x01 is IACCVIOL alone; MMARVALID (bit 7) is clear, so MMFAR is not valid. The faulting address is the stacked PC.
  2. Encode RBAR for an unprivileged, read-only, executable region starting at 0x000A0400.
    AnswerRO = 1, NP = 1 → AP = 0b11 → 0x6; XN = 0; SH = 0. RBAR = 0x000A0406. This is idx 0 in the measured dump.
  3. The port's dump prints a region limit of 0x200018A0. What is the last byte the region covers, and why?
    Answer0x200018BF. RLAR stores limit bits [31:5]; the low five bits of the limit are implicitly 1.
  4. Why did writing AGT0 at 0x400E8008 raise a MemManage fault rather than succeed through PRIVDEFENA?
    AnswerPRIVDEFENA gives the default map only to privileged accesses. The access came from an unprivileged partition and matched no enabled region, so it faulted.
  5. Construct EXC_RETURN for "return to Secure Thread mode on PSP, no FP, default stacking rules, exception taken to Secure".
    AnswerPrefix and RES1 0xFFFFFF80, plus S 0x40, DCRS 0x20, FType 0x10, Mode 0x08, SPSEL 0x04, ES 0x01 = 0xFFFFFFFD — TF-M's EXC_RETURN_THREAD_PSP.
  6. HFSR = 0x40000000 and CFSR, SFSR are zero. What do you look for in the code?
    AnswerFORCED with no fault bits: an SVC that could not be taken because SVCall (priority 0 under TF-M) was masked — by PRIMASK or FAULTMASK, or because the SVC ran inside a handler already at priority 0. BASEPRI cannot do it: it only masks priorities at or below a non-zero value. Look for a logging or PSA call made before interrupts were re-enabled.
