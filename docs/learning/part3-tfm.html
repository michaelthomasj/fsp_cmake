Part 3 — TF-M

Trusted Firmware-M is Arm's reference implementation of the PSA Firmware Framework for M-profile. It is built entirely from the mechanisms in Parts 1 and 2: TrustZone separates the secure world from the non-secure one, the MPU and CONTROL.nPRIV separate pieces of the secure world from each other, and SVC and PendSV move between them.

Three documents, three kinds of claim:

  • PSA-FF-M (Firmware Framework for M) — the specification: what a secure partition is, what psa_call does, what each isolation level must guarantee.
  • TF-M one implementation of it, with its own choices (e.g. how isolation level 3 is realised with eight MPU regions).
  • This port what this repository supplies or changes.

3.2 psa_call, end to end

A client calls a service with psa_call(handle, type, in_vec, in_len, out_vec, out_len). The input and output vectors are lists of {pointer, length}; the service reads and writes them through the SPM (psa_read, psa_write), not by dereferencing the client's pointer directly. That is what lets the SPM check each vector against the caller's boundary with tfm_hal_memory_check(), once, when the call is made. The exception is MM-IOVEC (psa_map_invec/psa_map_outvec), which lets a service map client memory directly; it is allowed only at isolation 1 (config/check_config.cmake:14) and is OFF here (PSA_FRAMEWORK_HAS_MM_IOVEC, config/config_base.cmake:67). The Crypto manifest above declares "mm_iovec": "enable" in the elided part, which has no effect while that option is OFF.

Under the SFN backend the same call has no PendSV and no second thread: the SPM looks up the service and calls its function directly on the caller's stack (§3.5).

3.3 Isolation levels 1, 2, 3 — precisely what each adds

PSA-FF-M defines three levels, each a superset of the one before:

  1. SPE is isolated from NSPE.
  2. …and PSA RoT is isolated from Application RoT.
  3. …and each secure partition is isolated from the others.

Things level 3 does not do in TF-M's Armv8-M HAL, which follow directly from the code:

  • Code is not isolated between ARoT partitions. All unprivileged and ARoT code is one read-only, executable region (idx 0). Every ARoT partition can read and execute every other's code.
  • PSA RoT partitions are not isolated from each other or from the SPM. They are privileged, and tfm_hal_activate_boundary() returns before touching the MPU for a privileged partition (:575-578).

3.4 PSA Certified Level 3 is not isolation level 3

Two independent numbering schemes share the words "level 3":

TF-M / PSA-FF-M isolation levelPSA Certified level
What it isa firmware build option: how many boundaries the SPM enforcesan assurance level of an independent security evaluation of a product
Set by-DTFM_ISOLATION_LEVEL=the scope and attack model of the evaluation (from questionnaire review up to lab testing that includes hardware attacks)
Changeswhich partitions are privileged and how the MPU is usednothing in the code

A part certified at PSA Certified Level 2 or 3 may be running TF-M at any isolation level its evaluation accepted, and building TF-M at isolation level 3 certifies nothing. The PSA Certified column is from PSA Certified's public scheme, not from this repository; check the current scheme documents for what each level requires.

3.6 Interrupts: FLIH and SLIH, and why the handler is in Thread mode

A partition that owns an interrupt declares it in its manifest and chooses a handling model:

  • SLIH (Second-Level): the SPM disables the interrupt and asserts a signal; the partition handles it later in its own thread, then re-enables it.
  • FLIH (First-Level): a partition-supplied function runs in the interrupt's context, immediately, and returns whether to also signal the partition.

The platform's vector entry calls spm_handle_interrupt(). For FLIH:

        /* FLIH Model Handling */
#if TFM_ISOLATION_LEVEL == 1
        flih_result = p_ildi->flih_func();
        (void)fih_bool;
#else
        FIH_CALL(tfm_hal_boundary_need_switch, fih_bool,
                 spm_boundary, p_pt->boundary);
        if (fih_eq(fih_bool, fih_int_encode(false))) {
            flih_result = p_ildi->flih_func();
        } else {
            flih_result = tfm_flih_deprivileged_handling(
                                                p_pt,
                                                (uintptr_t)p_ildi->flih_func,
                                                GET_CURRENT_COMPONENT());
        }
#endif

secure_fw/spm/core/interrupt.c:194-209

  • At level 1, or when the owner is privileged (PSA RoT), the FLIH function is called directly, in Handler mode.
  • Otherwise tfm_flih_deprivileged_handling() executes SVC TFM_SVC_PREPARE_DEPRIV_FLIH (interrupt.c:33-40). The SVC handler activates the owner's boundary (sets nPRIV = 1), builds a fresh thread context on the owner's stack, and returns EXC_RETURN_THREAD_PSP (interrupt.c:42-102; tfm_arch.c:165). The exception return lands in Thread mode, unprivileged, at the FLIH function. When it returns, a second SVC (TFM_SVC_FLIH_FUNC_RETURN) restores the interrupted context (interrupt.c:105-150).

Handler mode is the usual case. D113 first wrote this up as "TF-M runs FLIH handlers in THREAD mode" — the third row stated as a rule. It was the case being measured: a correct observation, a wrong generalisation. D117 corrected it to this table.

The architecture says Handler mode is always privileged. TF-M arranges for an Application-RoT FLIH handler above isolation 1 not to run in Handler mode. Both statements are true. The design choice is intentional: an interrupt handler written by an Application-RoT developer gets the permissions that developer's partition has, no more.

The TF-M memory map on RA6M5

The boundary handle

tfm_hal_bind_boundary() returns an opaque uintptr_t the SPM stores per partition and passes back later. Its encoding (:363-378):

  • Levels 1/2: bit 1 privileged, bit 0 "is the TrustZone NS agent". Handles need not be unique.
  • Level 3: additionally up to five 4-bit MMIO descriptors (3-bit index into the allow-list + RW bit) and an 8-bit unique index in bits 31:24 — up to 256 boundaries (:380-385).

The SPM's own handle, PROT_BOUNDARY_VAL, has the privileged bit (and at level 3 an SPM bit) set (:45-47, :55-56). tfm_hal_boundary_need_switch() then reduces to: "different handles, and not both privileged".

Bind, at level 2

For each mmio_region asset of an unprivileged partition (:456-502): check the region is 32-byte aligned at both ends — (periph_start & ~MPU_RBAR_BASE_Msk) == 0 and (periph_limit & ~MPU_RLAR_LIMIT_Msk) == 0x1F — then append it at index n_static_regions++. The post-increment matters: the "static" count grows, so these regions are never cleared afterwards. At level 2 every unprivileged partition can therefore reach every other unprivileged partition's peripherals; separating those is what level 3 adds.

Activate, at level 3

For an unprivileged partition (:575-680): disable the MPU; program each runtime-memory asset (the partition's own data) as an unprivileged RW region from index n_static_regions; decode the MMIO descriptors from the handle and program each; clear every remaining region; re-enable. Every context switch between ARoT partitions rewrites the MPU.

RA6M5 and RA8M2 both have 8 regions and five static, which leaves 8 − 5 = 3 regions per partition at level 3 for private data plus MMIO. RA8M2's measured static set has the same shape at different addresses — code from 0x02068400 in MRAM, data from 0x22000400, AGT0 at 0x40221000 (D115).

Read D113 to D126 in order afterwards: each later entry corrects something an earlier one stated too broadly.

The method lessons, as the log records them

  1. Read the compile line before trusting the source. Four rounds were spent verifying the manifest, allow-list, platform_data_t and alignment — all correct — before anyone asked whether the code consuming them was compiled in (D113).
  2. When a missing definition is found, enumerate what else the same translation unit depends on. One grep over the file's #if/#ifdef conditions would have found the second macro in the same pass (D114).
  3. Link the interface the code depends on; do not add macros one by one, because the macro-by-macro fix only finds the ones someone has already been bitten by (D114). The follow-up sharpened this: the HAL always depended on psa_interface, and every upstream platform supplies it by compiling the HAL in tfm_spm. The port's first fix was macro-by-macro, chosen to keep the shared-file delta small; D121 replaced it with the move, which fixes the class.
  4. Before calling a gap upstream, compare your port with the platforms that work. The missing macro was attributed to TF-M for four entries and then to a configuration option. One check would have settled it: which target does every other platform add this source to? Nine say tfm_spm; this port said platform_s.
  5. A macro absent from the compile line may be unset rather than unplumbed. TFM_PXN_ENABLE defaults OFF, so $<$<BOOL:OFF>:…> collapses to nothing; D114 read that absence as "never plumbed" (D115; box below).
  6. An unconditional #define of a config macro whose implementation is conditionally compiled is a latent link error. The port enabled CONFIG_TFM_POST_PARTITION_INIT_HOOK unconditionally, but the hook body sits inside #ifdef CONFIG_TFM_ENABLE_MEMORY_PROTECT. Every isolation-1 build has the call site (spm_ipc.c:435-440) without the body: spm_ipc.c is compiled unconditionally (secure_fw/spm/CMakeLists.txt:54) and SFN reaches it through BACKEND_SPM_INIT() (include/ffm/backend_sfn.h:14). L1+IPC failed only because it was the one level-1 tree rebuilt in between. D115 said SFN had no call site; D126 §1 corrected it. Now gated on the same macro (ra6m5/config_tfm_target.h:130-132; D115).
  7. A question closed because the symptom went away is not answered. D116 closed the L1+IPC boot-order question "by irrelevance"; D117 found the mechanism in the same two files.

3.9 FSP drivers inside partitions

Everything above decides where an FSP driver call may run. ADDING_FSP_MODULES.md §7 is the full account; the reasoning, using this course's vocabulary:

What an FSP call touchesWhere it livesFrom an unprivileged ARoT partition
driver code (compiled into platform_s)idx 1, PSA RoT codeIACCVIOL, MMFSR 0x01
the control block, e.g. g_timer0_ctrl in ra_gen/hal_data.c (0x2000fd54)idx 4, PSA RoT dataDACCVIOL, MMFSR 0x82
the NVIC, written by every interrupt-driven R_xxx_Open()PPBBusFault; no region can grant it

The third is architectural. R_AGT_Open() calls R_BSP_IrqCfgEnable(); the same pattern appears in r_spi (12 call sites), r_iic_master (7), r_sci_uart (5), r_canfd (5) (D113; the counts are not reproducible from these trees, D126 §6 — the point stands on R_AGT_Open() alone). It is a collision of models, not an FSP defect: TF-M takes NVIC ownership away from partitions (they declare irqs and use psa_irq_enable(), an SVC); FSP assumes the driver owns the interrupt controller. They disagree at _Open() and nowhere else.

This port splits the driver's lifetime by privilege:

  • _Open() in the privileged IRQ init hook (ra6m5/tfm_timer0_irq.c:120-140). It re-enables the IRQ in the NVIC, undoing FF-M's "arrives disabled" rule, so the port disables it again afterwards (:142-150).
  • Operational calls from the partition, touching only the peripheral's registers. The test fixture uses bare AGTCR writes because it has no control block of its own (ra6m5/plat_test.c:105-179).
  • Interrupt enable and disable through psa_irq_enable()/psa_irq_disable().

Or avoid the whole question: put the peripheral in a PSA RoT partition, which is privileged at every isolation level, where FSP works unmodified.

Check yourself

  1. At isolation level 1, does TF-M program the Secure MPU? Cite the line that decides.
    AnswerNo. CONFIG_TFM_ENABLE_MEMORY_PROTECT is defined only when the level is greater than 1 (or for PSA Arch IPC tests), platform/CMakeLists.txt:125, and the static table is compiled under it.
  2. At isolation 2, can Application-RoT partition A read partition B's mmio_region? At level 3?
    AnswerAt level 2, yes: MMIO regions are appended permanently at bind time and are unprivileged RW. At level 3, no: each partition's MMIO is programmed only while it runs.
  3. Why does the measured region count go 5 → 6 after partition init at level 2 but stay at 5 at level 3?
    AnswerLevel 2 appends the AGT0 region permanently in tfm_hal_bind_boundary(). Level 3 programs it in tfm_hal_activate_boundary() on each switch, after the post-partition dump has run.
  4. The FLIH handler of an Application-RoT partition runs at isolation 2. In which mode and at which privilege, and what makes it so?
    AnswerThread mode, unprivileged. spm_handle_interrupt() sees the owner's boundary differs from the SPM's and executes SVC TFM_SVC_PREPARE_DEPRIV_FLIH; the SVC handler activates the owner's boundary and returns with EXC_RETURN_THREAD_PSP into the FLIH function.
  5. Building TF-M at isolation level 3 makes a product "PSA Certified Level 3". True or false?
    AnswerFalse. They are unrelated scales: one is a build option, the other an evaluation assurance level.
  6. -DTFM_ISOLATION_LEVEL=2 -DCONFIG_TFM_SPM_BACKEND=SFN. What backend do you get?
    AnswerIPC: set_config.cmake loads the IPC defaults for any level above 1. D113 notes the pair is incoherent and surfaces as the manifest tool rejecting IPC-only test partitions.
  7. Which single compiler flag would have exposed the D113 defect at build time?
    Answer-Wundef, which warns when an undefined identifier is evaluated in #if.
  8. You must drive an SPI peripheral from an Application-RoT partition at isolation 2. Where does R_SPI_Open() go, and why?
    AnswerIn privileged init — the IRQ init hook the SPM calls — because it writes the NVIC, which is in the PPB and can never be granted to unprivileged code. Or make the partition PSA RoT.
