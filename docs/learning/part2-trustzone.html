Part 2 — TrustZone for Armv8-M

Privilege (Part 1) separates an operating system from its tasks. The Security Extension adds a second, independent axis that separates two whole software worlds, each with its own operating system. This part is where the architecture stops being enough: how an RA part attributes memory, interrupts and peripherals is Renesas's design, not Arm's.

2.1 Two security states, four quadrants

Armv8-M With the Security Extension the core is always in either Secure or Non-secure state. Every address is Secure, Non-secure, or Non-secure Callable (NSC). The core's state follows the attribution of the code it executes:

  • Secure state may access Secure and Non-secure memory.
  • Non-secure state may access only Non-secure memory. A Non-secure access to a Secure address raises a SecureFault (or, depending on where it is caught, a BusFault in Secure state); it never returns Secure data.
  • Security state and privilege are orthogonal: each state has its own privileged and unprivileged Thread mode and its own Handler mode.

The port's tfm_hal_memory_check() asks this two-axis question when a partition hands the SPM a buffer: is it accessible to this caller, privileged or not, Secure or not? It uses the CMSE intrinsic cmse_check_address_range(), which compiles to the TT (Test Target) instruction that reports both the MPU permission and the SAU/IDAU attribution of an address:

    if (!((uint32_t)boundary & HANDLE_ATTR_PRIV_MASK)) {
        flags |= CMSE_MPU_UNPRIV;
    }
    ...
    if (cmse_check_address_range((void *)base, size, flags) != NULL) {

2.2 SAU and IDAU — who decides what is secure

Armv8-M Two units attribute each address, and the result is the more secure of the two answers (Secure > NSC > Non-secure):

SAU — Security Attribution UnitIDAU — Implementation-Defined Attribution Unit
Defined byArm; registers at 0xE000EDD0the silicon vendor; outside the core
Programmed bySecure privileged software, at run timewhatever the vendor decides — on RA, boundary registers burned at provisioning
RegionsSAU_TYPE.SREGION; may be zerovendor-defined
DefaultSAU_CTRL.ENABLE = 0, ALLNS = 0 ⇒ everything Secure—

Because the more secure answer wins, the SAU can only make memory more secure than the IDAU says, never less. SAU_CTRL.ALLNS = 1 with the SAU disabled means "the SAU says Non-secure everywhere", which hands the decision entirely to the IDAU.

Why __SAUREGION_PRESENT is 0 on RA6M5 and 1 on RA8M2

RA The CMSIS device header declares whether the SAU has any regions: __SAUREGION_PRESENT 0 at R7FA6M5BH.h:47, 1 at R7KA8M2JF_core0.h:49. FSP's R_BSP_SAUInit() branches on it:

void R_BSP_SAUInit (void)
{
  #if __SAUREGION_PRESENT
    ...
    /* Configure SAU region used for Code Flash Non-secure callable. */
    SAU->RNR  = BSP_SAU_REGION_CODE_FLASH_NSC;
    ...
    /* Enable the SAU. */
    SAU->CTRL = SAU_CTRL_ENABLE_Msk;
    ...
  #else

    /* Setting SAU_CTRL.ALLNS to 1 allows the security attribution of all addresses to be set by the IDAU in the
     * system. */
    SAU->CTRL = SAU_CTRL_ALLNS_Msk;
  #endif
}

ra6m5_gcc_secure/ra/fsp/src/bsp/mcu/all/bsp_security.c:200-279

  • RA6M5: an SAU with zero regions. Armv8-M with the Security Extension always implements SAU_CTRL; __SAUREGION_PRESENT 0 means it has no regions to program. In the secure image FSP sets ALLNS, so the IDAU decides everything. There is one address alias for code flash (BSP_FEATURE_TZ_NS_OFFSET 0x00), so an address is Secure or Non-secure purely by which side of a boundary it falls.
  • RA8M2: SAU regions exist, and the part has two aliases of MRAM, 0x1000_0000 apart. The IDAU makes the high alias Non-secure, but with the SAU at its reset default every address is Secure, and the more secure answer wins. A Secure access to the Non-secure alias is then refused.

This port BL2 is a flat build on both parts, so FSP's R_BSP_SAUInit() never runs there and SAU_CTRL stays at reset: ENABLE = 0, ALLNS = 0, every address Secure — on RA6M5 too. RA6M5's BL2 is unaffected because there is only one alias: a Secure access to the IDAU-Non-secure flash is permitted, and it reaches the bytes at their only address. RA8M2's BL2 must read the Non-secure alias, so it has to enable the SAU itself:

Its bl2_boot_hal.c programs one SAU region over the Non-secure alias and enables the SAU (ra8m2/bl2_boot_hal.c:91-95); without it BL2's load from 0x120B0000 goes out as a Secure transaction and is refused. FSP's R_BSP_SAUInit() would do this, but only under BSP_TZ_SECURE_BUILD, and BL2 is a flat, TrustZone-unaware FSP project.

sau_and_idau_cfg() in ra6m5/target_cfg.c is empty by design: the shared HAL calls it (tfm_hal_isolation_v8m.c:275), and on RA6 the IDAU attributes everything once FSP has set SAU_CTRL.ALLNS (bsp_security.c:277).

The IDAU on RA: boundary registers

RA RA6M5 (RA6 family). The IDAU is driven by boundary registers in the PSCU, set once per device by the Renesas Device Partition Manager (RDPM). FSP could write them, but the code that would is compiled out (#if 0 == BSP_FEATURE_TZ_HAS_DLM; BSP_FEATURE_TZ_HAS_DLM (1UL) at ra6m5_gcc_secure/ra/fsp/src/bsp/mcu/ra6m5/bsp_feature.h:599).

RA RA8M2 is different. Its PSCU has only CFSAMONA, and that one is read-only (__IM, offset 0x30, R7KA8M2JF_core0.h:3560); RDPM sets the code-MRAM boundary CFS2. FSP writes the SRAM Secure/Non-secure split at boot into R_CPSCU->SRAMSABAR0..3 (ra8m2_gcc_CPU0_secure/ra/fsp/src/bsp/mcu/all/bsp_security.c:202-211). NSC on RA8M2 comes from SAU regions. BSP_FEATURE_TZ_HAS_DLM is also 1 there (…/mcu/ra8m2/bsp_feature.h:597), so the RA6-style block stays compiled out.

The coarse granularities constrain the layout: Secure + NSC code must be a multiple of 32 KB, Secure + NSC SRAM a multiple of 8 KB. Each part's values are derived against that rule in its part guide (RA6M5_SOLUTION.md).

2.3 Non-secure-callable memory and SG veneers

Armv8-M Non-secure code may not branch to an arbitrary Secure address — otherwise it could jump into the middle of a secure function after its checks. The rule:

  • The only legal target of a Non-secure → Secure branch is an SG (Secure Gateway) instruction located in memory attributed NSC.
  • Any other target raises SecureFault with SFSR.INVEP (bit 0), before the target instruction runs.
  • Secure code returns with BXNS LR and calls Non-secure functions with BLXNS. The compiler clears registers that might leak Secure values before either.

With CMSE (-mcmse), a function declared cmse_nonsecure_entry gets a small veneer — SG followed by a branch to the real function — emitted into the .gnu.sgstubs section. The linker must place that section inside the NSC window.

This port The NSC window comes from the e2 solution and the veneers are pinned to it rather than allowed to float to the end of the code:

#define CMSE_VENEER_REGION_START        (BSP_PARTITION_FLASH_CPU0_C_START)
#define CMSE_VENEER_REGION_SIZE         (BSP_PARTITION_FLASH_CPU0_C_SIZE)
...
#define TFM_LINKER_VENEERS_START        CMSE_VENEER_REGION_START
...
#define TFM_LINKER_VENEERS_LOCATION_END

ra6m5/region_defs.h:173-183. On RA6M5 the window is FLASH_CM33_C, 0x11F800, 2 KB (RA6M5_SOLUTION.md).

Pinned because the RA boundaries are set once at provisioning: if the veneers moved with each build, a firmware update could move them out of the window the part was provisioned with (DESIGN.md §7).

        "   bne    reent_panic4                               \n"

The stack-seal comparison is a re-entrancy check: on Armv8.0-M the hardware does not detect a Non-secure caller re-entering Secure state while a Secure call is in progress, so TF-M checks for its seal pattern itself (comment at psa_api_veneers_v80m.c:21-33). Armv8.1-M parts such as the RA8M2's Cortex-M85 use psa_api_veneers.c instead (secure_fw/partitions/ns_agent_tz/CMakeLists.txt:35-36).

Three ways this port has hit INVEP

  • Veneers outside the window. A linker script that ignores TFM_LINKER_VENEERS_LOCATION_END places veneers outside NSC; the fault PC is a *_veneer symbol (UPSTREAM_CHANGES.md item 2).
  • Boundaries never programmed. On an unprovisioned part everything is Secure and the first BLXNS faults.
  • Boundaries reprogrammed by the debugger. setTZBoundaries must be false: GETTING_STARTED.md §6.

2.4 Banked registers

Armv8-M Many core registers exist twice, once per security state. Code always sees the copy for its current state at the normal address. Secure code reaches the Non-secure copy through the non-secure alias of the System Control Space at 0xE002E000 or, for special registers, through MRS/MSR with an _NS suffix. Non-secure code cannot reach the Secure copy at all.

Banked (one copy per state)Secure-onlyShared
MSP, PSP, MSPLIM, PSPLIM · CONTROL (nPRIV, SPSEL) · PRIMASK, BASEPRI, FAULTMASK · VTOR · the MPU (a Secure and a Non-secure MPU) · SysTick, where both are implemented · parts of the SCB, e.g. SHCSR, CCR, CPACR, the MemManage status the SAU · NVIC_ITNS · SFSR, SFAR · NSACR · AIRCR.PRIS, AIRCR.BFHFNMINS R0–R12, LR, PC, xPSR · FP registers (with FPCCR rules to clear them on return) · NVIC enable/pending/priority — not banked. Secure sees every interrupt; Non-secure sees only those with ITNS = 1

Examples of TF-M reaching across:

  • __TZ_get_CONTROL_NS() to learn whether the Non-secure caller was privileged (tfm_hal_isolation_v8m.c:719).
  • __TZ_set_PRIMASK_NS(1) as TFM_NS_EXC_DISABLE() (tfm_arch_v8m.h:46-49).
  • SCB_NS->CPACR to disable the FPU for the Non-secure side (tfm_arch_v8m_main.c:316).

The MPU is banked. When this course says "the MPU" in Part 1 and Part 3 it means the Secure MPU, MPU_S, which TF-M owns. The non-secure RTOS has its own, independent MPU. D113 and D115 counted 8 regions on the Secure MPUs of RA6M5 and RA8M2; the count need not be the same for the Non-secure one, and this port has not read it.

2.5 The NVIC target-state mechanism, and priority partitioning

Armv8-M Each external interrupt has a bit in NVIC_ITNS (0xE000E380): 0 targets Secure state, 1 Non-secure. Only Secure code can write it. A Secure-targeted interrupt is invisible to Non-secure software — reads as zero, writes ignored.

Two AIRCR bits complete the picture:

  • BFHFNMINS — if 0 (reset), BusFault, HardFault and NMI target Secure state. TF-M leaves it at 0.
  • PRIS — "prioritise Secure". When set, every Non-secure priority is mapped into the lower-urgency half: a Non-secure priority p behaves as 0x80 + p/2. Non-secure code can therefore never preempt a Secure exception at priority below 0x80, even by raising its own BASEPRI.

TF-M sets PRIS before any partition runs:

    /* Set PRIS flag in AIRCR */
    AIRCR = scb->AIRCR;
    VECTKEY = (~AIRCR & SCB_AIRCR_VECTKEYSTAT_Msk);
    scb->AIRCR = SCB_AIRCR_PRIS_Msk |
                 VECTKEY |
                 (AIRCR & ~SCB_AIRCR_VECTKEY_Msk);

tfm_arch_v8m_main.c:231-236, called from main() at secure_fw/spm/core/main.c:122

Now the PendSV value from Part 0 makes sense. TF-M wants its scheduler at the lowest Secure priority, but still above everything Non-secure code can reach:

 * When AIRCR.PRIS is set, the Non-Secure execution can act on
 * FAULTMASK_NS, PRIMASK_NS or BASEPRI_NS register to boost its priority
 * number up to the value 0x80.
 * For this reason, set the priority of the PendSV interrupt to the next
 * priority level configurable on the platform, just below 0x80.
 */
#define PENDSV_PRIO_FOR_SCHED ((1 << (__NVIC_PRIO_BITS - 1)) - 1)

secure_fw/spm/include/tfm_arch.h:63-69. With 4 priority bits: 7, i.e. 0x70.

2.6 Interrupts on RA: two registers that must agree

RA On RA an interrupt's security state is held in two places: NVIC->ITNS (Arm) and R_CPSCU->ICUSARG (Renesas, for the ICU's event-link registers). FSP's bsp_irq_cfg() writes them together, from the same value, with the security-attribution registers unlocked:

    for (uint32_t i = 0U; i < BSP_ICU_VECTOR_MAX_ENTRIES / BSP_PRV_BITS_PER_WORD; i++)
    {
        p_icusarg[i]  = interrupt_security_state[i];
        NVIC->ITNS[i] = interrupt_security_state[i];
    }

ra6m5_gcc_secure/ra/fsp/src/bsp/mcu/all/bsp_irq.c:272-284

interrupt_security_state starts all-Non-secure and has a bit cleared for every slot with a non-zero entry in the generated event-link table. So:

On RA, an interrupt is Secure if and only if the secure e2 project configures it with a real interrupt priority (D061). It is a build-time property, set by the configurator.

TF-M Every Arm reference platform instead makes an interrupt Secure at run time by calling CMSIS NVIC_ClearTargetState() in the partition's IRQ init. This port does not: NVIC_ClearTargetState() writes only ITNS, so on RA it would leave ITNS and ICUSARG disagreeing (ra6m5/tfm_timer0_irq.c:18-22).

When the event-link table links as zeros

ra_gen/vector_data.c (the real g_interrupt_event_link_select[]) and FSP's bsp_irq.c (a weak all-zero copy) sit in the same static library. Because TF-M uses its own vector table, nothing references vector_data.o, so the weak copy wins and bsp_irq_cfg() programs no IELSR and leaves ITNS/ICUSARG Non-secure: the interrupt never fires. The port forces the real member in with an anchor:

extern const fsp_vector_t g_vector_table[];
const fsp_vector_t * const ra6m5_icu_vector_data_anchor = g_vector_table;

ra6m5/target_cfg.c:245-246. Diagnose it from the symbol binding (V weak, T strong) in the linked image.

This port TF-M's vector table, not FSP's, is the one installed, so each serviced slot is overridden by hand (Part 0 §0.5); FSP's ISRs would call driver callbacks directly and bypass the SPM.

2.7 Peripherals on RA: PSAR, not a PPC

A peripheral is just a range of addresses, so it could be attributed by the SAU/IDAU like memory. In practice SoCs need finer control. Two different designs exist:

The azone is where peripheral security lives

D112: a property-by-property diff of the RA8M2 IAR and GCC e2 projects showed them identical, yet the IAR project was missing an ICU.IRQ0 security assignment. Peripheral-to-zone assignments are stored in the .secure_azone file, which the diff never read. When checking that two projects attribute peripherals the same way, diff the azone too (PORTING.md §6).

Other RA security-attribution registers

R_BSP_SecurityInit() also writes LPMSAR, SRAMSAR and, on MRAM parts, MSAR. A Non-secure MRAM controller gives a precise BusFault at 0x4013C000 from Secure code: a security-attribution fault, not a privilege fault. Cause and workaround: RA8M2_SOLUTION.md; clock security: DESIGN.md §13.3.

2.8 Provisioning: the part of TrustZone no firmware sets

  • This port Boundary values are per part: take them from RA6M5_SOLUTION.md or RA8M2_SOLUTION.md. RDPM erases the part; follow GETTING_STARTED.md §6.
  • Verify by reading CFSAMONA back (and CFSAMONB on RA6); a wrong value is not a build error.

Check yourself

  1. The SAU says an address is Non-secure and the IDAU says it is NSC. What is it?
    AnswerNSC. The combined attribution is the more secure of the two, and NSC is more secure than Non-secure.
  2. Why does BL2 on RA8M2 need to enable the SAU, while BL2 on RA6M5 does not?
    AnswerNeither BL2 runs FSP's R_BSP_SAUInit(), so the SAU starts at its reset state and every access is treated as Secure. RA6M5 has one alias, and a Secure access to IDAU-Non-secure flash still reaches the bytes; RA8M2 must read the Non-secure MRAM alias, which refuses a Secure transaction.
  3. Non-secure code calls a function pointer that holds the address of a Secure function's first instruction (not its veneer). What happens, and which register records it?
    AnswerSecureFault with SFSR.INVEP: the target is not an SG instruction in NSC memory. SFSR is at 0xE000EDE4.
  4. Why is TF-M's PendSV priority 0x70 rather than 0xF0?
    AnswerWith AIRCR.PRIS set, Non-secure code can boost itself to an effective priority of 0x80. PendSV must remain above that so Non-secure code can never mask or preempt the secure scheduler; 0x70 is the least urgent level below 0x80 with 4 priority bits.
  5. An Arm porting guide says to call NVIC_ClearTargetState(irq) in your IRQ init. Why is that wrong on RA?
    AnswerRA keeps target state in both NVIC->ITNS and ICUSARG, and they must agree. The CMSIS call writes only ITNS. FSP has already set both from the secure project's configuration.
  6. An interrupt you configured in the secure e2 project never fires, and IELSR[n] reads 0. Name the first thing to check in the linked image.
    AnswerWhether g_interrupt_event_link_select is the strong definition from vector_data.c (T) or FSP's weak zero fallback (V), and its contents (D069).
  7. RA6M5 has no PPC. What does TF-M's call to ppc_configure_to_secure() do on this port, and where is the peripheral's security set?
    AnswerNothing — it is a no-op, and is never reached because every platform_data_t carries PPC_SP_DO_NOT_CONFIGURE. Security is set in the PSCU's PSAR registers by FSP's R_BSP_SecurityInit(), from the e2 project's configuration.
