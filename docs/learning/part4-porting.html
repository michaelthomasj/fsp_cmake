Part 4 — Porting

A port is the glue between TF-M's assumptions and one part's reality. This page is the map; the operational detail is in PORTING.md, ADDING_FSP_MODULES.md, GETTING_STARTED.md and CONFIGURATION.md, which this page cites rather than repeats.

4.1 The platform contract

TF-M A platform is a directory, platform/ext/target/<vendor>/<part>/, selected by -DTFM_PLATFORM=renesas/ra6m5. It resolves by path; there is no registry to edit (PORTING.md §1). What the directory must provide, grouped by the parts of this course that explain why:

4.4 Consuming FSP in the TF-M build

FSP drivers are opt-in, per role: nothing from ra/fsp/src/ reaches an image unless a cmake/modules/fsp_<name>.cmake declares it and the platform lists it in FSP_MODULES_S or FSP_MODULES_BL2 (ADDING_FSP_MODULES.md §1–3). Each module builds once per role (fsp_bsp_s, fsp_bsp_bl2) because the secure image and BL2 come from different e2 projects.

Three problems specific to running FSP under TF-M, each with a decision behind it:

  1. Start-up order. TF-M's Reset_Handler calls SystemInit() before the C runtime zeroes .bss (Part 0 §0.5). FSP state computed there, such as SystemCoreClock, is then wiped; R_FLASH_HP_Open() derived FCLK = 0 and returned FSP_ERR_FCLK. FSP's own remedy is BSP_CFG_EARLY_INIT = 1, which places such state in .ram_noinit; the port asserts it at build time and also re-runs SystemCoreClockUpdate() in tfm_hal_platform_init() (DESIGN.md §8.1, D034). The non-secure image is unaffected: it uses FSP's own start-up.
  2. Static libraries and weak symbols. FSP compiled into an archive can silently lose a strong definition to a weak one (D069, Part 2 §2.6). The port anchors g_vector_table to force the right member in.
  3. Privilege. FSP drivers assume they own the NVIC. From isolation 2, Application-RoT partitions cannot call _Open() (Part 3 §3.9). The module mechanism puts driver code in platform_s, i.e. PSA RoT code; code an ARoT partition calls must go in tfm_sprt and be stateless (ADDING_FSP_MODULES.md §7).

The build warns about drivers enabled in e2 but claimed by no module. D069 records that the warning correctly named the missing r_agt module through two failed hardware runs before anyone read it.

4.5 Flash layout and MCUboot

Three images, three linker scripts, one part. BL2 (MCUboot) lives at the base of flash, verifies the two signed images, and jumps to the secure one, which later jumps to the non-secure one.

RA6M5_SOLUTION.md §Layout. Every boundary is a multiple of the 32 KB erase block.

  • Slot order is not what you would assume. The secure secondary slot is below the primary on RA6M5, and on RA8M2 (PORTING.md §2, D100). Read the generated symbols.
  • Overwrite-only upgrade. The scratch block is reserved so a later move to swap mode needs no re-provisioning, and is Secure because during a swap it would hold secure-image fragments.
  • MCUBOOT_ALIGN_VAL is a flag day: 128 on RA6M5, 32 on RA8M2. imgtool encodes it in the trailer, so images are not interchangeable between parts (CONFIGURATION.md §3). TF-M's choice list stopped at 32; extending it is upstream item 6.
  • FLASH_AREA_IMAGE_SECTOR_SIZE restates an FSP value and nothing checks it: at 0x1000 against FSP's 0x8000, slots were 9.875 sectors long, every build step accepted it, and it failed on hardware as BOOT_EFLASH (D054).
  • Who owns the MCUboot flash backend took three attempts to settle (D075–D091). Settled: TF-M's map and backend, with FSP's driver wrapped as a CMSIS ARM_DRIVER_FLASH behind fa_driver — the arrangement ST uses for STM32Cube (DESIGN.md §4, D091).

Tabulating documents go stale first. Until D117, CONFIGURATION.md §3 and the header of RA8M2_SOLUTION.md still listed DEFAULT_MCUBOOT_FLASH_MAP and DEFAULT_MCUBOOT_FLASH_BACKEND as OFF, citing the entries D091 superseded — although neither variable was set in either config.cmake any more. Both now point at DESIGN.md §4, which had stayed correct throughout. D117's observation: the document that explains why stayed right; the two that tabulate what did not.

Measured boot is verified from RAM, not from a test suite

BL2 writes a boot record into the first 0x400 bytes of secure RAM (BOOT_TFM_SHARED_DATA_BASE = S_DATA_START, ra6m5/region_defs.h:227-228). The attestation suite passes even when that record is empty — the token then carries IAT_NO_SW_COMPONENTS — so the earlier attestation passes were on a token with no measurements (D080). Verify by reading the record and matching both measurements to the images' SHA-256 TLVs (D081, D096).

4.6 Where the rest of this lives

Three subjects a porter needs are owned by the repository documents rather than by this course, and restating them here would give you two versions to reconcile. What each one is, and where to read it:

SubjectWhy it matters to a portRead
The two hazards that cost hardware Option-setting memory must be linked one word per MEMORY region, and the debugger must never program the TrustZone boundaries. Both failures are silent, and the first one is not recoverable. DESIGN.md §8.4 for the mechanism, GETTING_STARTED.md §6 for the checks to run before flashing
Verification gates What a new part has to pass before anyone trusts it, in order, so that a failure points at one thing. PORTING.md
Divergence from upstream TF-M 24 files of common code are modified, every one of them a gap or defect any platform with the same property would hit. A port that does not know which they are cannot survive a TF-M uprev. UPSTREAM_CHANGES.md
What a generated project must supply The contract between RASC and the build: the partition symbols, the modules, the settings that are load-bearing. Most of it is enforced at build time. E2_PROJECT_REQUIREMENTS.md

This port The one habit worth carrying from all four: each hazard gets a mechanism, not a comment. Every rule above is enforced by something that fails the build or the flash — a guard script, an #error, a layout assertion — because a rule that lives only in prose is a rule someone will read after the board is dead.

Check yourself

  1. You change a partition size in the e2 solution. Which files in the TF-M platform directory do you edit?
    AnswerIdeally none: flash_layout.h and region_defs.h derive from BSP_PARTITION_*. You rebuild the e2 project, rebuild TF-M, let <part>_layout_checks.c assert, and — if a TrustZone boundary moved — re-run RDPM and reflash everything. PS capacity and the NSC budget do not follow automatically.
  2. Why must BL2 on a TF-M-started image either set BSP_CFG_EARLY_INIT or recompute SystemCoreClock, while the non-secure image need not?
    AnswerTF-M's Reset_Handler runs SystemInit() before .bss is zeroed, wiping state FSP computed. The non-secure image uses FSP's own start-up, which runs in the order FSP expects.
  3. A colleague flashes bl2.bin from an old build directory. What is the risk and how do you tell from the file listing?
    AnswerA flat binary spanning the option memory writes zeros across it and can permanently lock the part. Size is the tell: over about 1 MB means it spans option memory (0x0100Axxx on RA6 parts, 0x02C9Fxxx on RA8M2).
  4. The attestation suite passes. Has measured boot been demonstrated?
    AnswerNo. It passes with IAT_NO_SW_COMPONENTS. Read the boot record at the start of secure RAM and match the measurements to the image TLVs.
  5. Your new RA8 port passes every gate at isolation 1. Name two defects classes that could still be present.
    AnswerAnything the MPU would catch — ARoT code or data in privileged regions, missing MMIO grants, FLIH handlers touching unmapped registers — because the MPU is off at level 1; and isolation-HAL macros that do not reach the target compiling the HAL (check it is tfm_spm, as upstream does). And any build-only defect in a configuration you did not build, like the isolation-1 hook link error (D115, D126 §1).
  6. Why is item 13 in UPSTREAM_CHANGES.md kept although withdrawn?
    AnswerTo record the observation behind it: DEFAULT_MCUBOOT_FLASH_MAP=OFF replaces only the map data, not the backend, and the port no longer needs to replace the backend because FSP's HAL sits behind TF-M's fa_driver (D091).
