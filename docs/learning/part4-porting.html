Part 4 — Porting

A port is the glue between TF-M's assumptions and one part's reality. This page is the map; the operational detail is in PORTING.md, ADDING_FSP_MODULES.md, GETTING_STARTED.md and CONFIGURATION.md, which this page cites rather than repeats.

4.1 The platform contract

4.4 Consuming FSP in the TF-M build

FSP drivers are opt-in for the secure and BL2 images: nothing from ra/fsp/src/ reaches them unless a cmake/modules/fsp_<name>.cmake declares it and the platform lists it in FSP_MODULES_S or FSP_MODULES_BL2. The non-secure image takes every enabled module (ADDING_FSP_MODULES.md §1–3).

Three problems specific to running FSP under TF-M, each with a decision behind it:

  1. Start-up order. TF-M's Reset_Handler calls SystemInit() before the C runtime zeroes .bss (Part 0 §0.5), so FSP state computed there, such as SystemCoreClock, is wiped. The required BSP_CFG_EARLY_INIT setting is in E2_PROJECT_REQUIREMENTS.md §5 ("Early BSP Initialization"). The non-secure image is unaffected, because it uses FSP's own start-up and so zeroes .bss before SystemInit() runs.
  2. Static libraries and weak symbols. FSP compiled into an archive can silently lose a strong definition to a weak one (D069, Part 2 §2.6). The port anchors g_vector_table to force the right member in.
  3. Privilege. FSP drivers assume they own the NVIC. From isolation 2, Application-RoT partitions cannot call _Open() (Part 3 §3.9). The module mechanism puts driver code in platform_s, i.e. PSA RoT code; code an ARoT partition calls must go in tfm_sprt and be stateless (ADDING_FSP_MODULES.md §7).

The build warns about drivers enabled in e2 but claimed by no module; treat that warning as an error.

4.5 Flash layout and MCUboot

Three images, three linker scripts, one part. BL2 (MCUboot) lives at the base of flash, verifies the two signed images, and jumps to the secure one, which later jumps to the non-secure one.

The order is the part of this a porter has to absorb, and two things in it are not what you would assume. RA6M5, reading up from the base of flash: BL2, the reserved scratch block, the secure secondary slot, the secure primary slot with the non-secure-callable veneers pinned at its top, then the two non-secure slots, with ITS, PS and the NV counters in data flash. Every address and size is in RA6M5_SOLUTION.md, which owns the layout.

Every boundary is a multiple of the 32 KB erase block.

  • Slot order is not what you would assume. The secure secondary slot is below the primary on RA6M5, and on RA8M2 (PORTING.md §2, D100). Read the generated symbols.
  • Overwrite-only upgrade. The scratch block is reserved so a later move to swap mode needs no re-provisioning, and is Secure because during a swap it would hold secure-image fragments.
  • MCUBOOT_ALIGN_VAL differs per part, so signed images are not interchangeable between parts (CONFIGURATION.md §3).
  • FLASH_AREA_IMAGE_SECTOR_SIZE restates an FSP value and nothing checks it, so a mismatch passes every build step and fails only on hardware (DESIGN.md §4).
  • MCUboot flash backend: TF-M's map and backend, with FSP's driver wrapped as a CMSIS ARM_DRIVER_FLASH behind fa_driver (DESIGN.md §4).

Measured boot is verified from RAM, not from a test suite

BL2 writes a boot record into the first 0x400 bytes of secure RAM (BOOT_TFM_SHARED_DATA_BASE = S_DATA_START, ra6m5/region_defs.h:227-228). The attestation suite passes even when that record is empty — the token then carries IAT_NO_SW_COMPONENTS. Verify by reading the record and matching both measurements to the images' SHA-256 TLVs.

4.6 Where the rest of this lives

Four subjects a porter needs are owned by other documents:

SubjectWhy it matters to a portRead
The two hazards that cost hardware Option-setting memory must be linked with one MEMORY region per option group — a group can be wider than a word, so the rule is per group, not per word — and the debugger must never program the TrustZone boundaries. Both failures are silent, and the first one is not recoverable. DESIGN.md §8.4 for the mechanism, GETTING_STARTED.md §6 for the checks to run before flashing
Verification gates What a new part has to pass before anyone trusts it, in order, so that a failure points at one thing. PORTING.md
Divergence from upstream TF-M 24 files of common code are modified, every one of them a gap or defect any platform with the same property would hit. A port that does not know which they are cannot survive a TF-M uprev. UPSTREAM_CHANGES.md
What a generated project must supply The contract between RASC and the build: the partition symbols, the modules, the settings that are load-bearing. Most of it is enforced at build time. E2_PROJECT_REQUIREMENTS.md

This port Each hazard is enforced by something that fails the build or the flash — a guard script, an #error, a layout assertion — not by prose alone.

Check yourself

  1. You change a partition size in the e2 solution. Which files in the TF-M platform directory do you edit?
    AnswerIdeally none: flash_layout.h and region_defs.h derive from BSP_PARTITION_*. You rebuild the e2 project, rebuild TF-M, let <part>_layout_checks.c assert, and — if a TrustZone boundary moved — re-run RDPM and reflash everything. PS capacity and the NSC budget do not follow automatically.
  2. Why must the secure image and BL2 either set BSP_CFG_EARLY_INIT or recompute SystemCoreClock, while the non-secure image need not?
    AnswerTF-M's Reset_Handler runs SystemInit() before .bss is zeroed, wiping state FSP computed. The non-secure image uses FSP's own start-up, which runs in the order FSP expects.
  3. The attestation suite passes. Has measured boot been demonstrated?
    AnswerNo. It passes with IAT_NO_SW_COMPONENTS. Read the boot record at the start of secure RAM and match the measurements to the image TLVs.
  4. Your new RA8 port passes every gate at isolation 1. Name two defects classes that could still be present.
    AnswerAnything the MPU would catch — ARoT code or data in privileged regions, missing MMIO grants, FLIH handlers touching unmapped registers — because the MPU is off at level 1; and isolation-HAL macros that do not reach the target compiling the HAL (check it is tfm_spm, as upstream does). And any build-only defect in a configuration you did not build, like the isolation-1 hook link error (D115, D126 §1).
