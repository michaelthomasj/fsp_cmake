Project Plan · Revised after stakeholder review

TF-M on Renesas RA — RA6 → RA8x2 (dual-core), FSP 6.6, GNUARM + IAR

Stakeholders want RA8x2 (dual-core) running Trusted Firmware-M — which means binding FSP inter-core communication to TF-M's mailbox HAL. IAR is required; RA6 is finished first on both toolchains as the foundation. Validation is deliberately light — a boot test plus a basic-crypto NSC app to prove the S → NS / veneer path — not a psa-arch-tests suite. All dates are targets; a slip is preferred to cutting the dual-core scope.

Platform HAL surface — what each target must implement

Boot & isolation

  • startup + linker, OFS (BL2)
  • target_cfg.c — SAU / PPC / MPC
  • tfm_hal_isolation.c; DDSC bridge (gp_ddsc_*)

Multi-core (RA8x2)

  • tfm_hal_multi_core_* + platform_mailbox over FSP ICC
  • NS mailbox agent
  • PSA call marshaling across cores

Storage

  • Driver_FLASH0/1 (code + data)
  • its_flash_fs HAL (ITS)
  • ps_nv_counters (PS)

Crypto & entropy

  • RSIP crypto driver
  • entropy / TRNG source
  • crypto key HAL (exercised by the NSC app)

Identity & provisioning

  • OTP HAL + lifecycle state
  • IAK + BL2 ROTPKs (dummy for dev)
  • NV counters backend

Platform service & NS

  • system reset, IOCTL, NV-counter API
  • NS ns/CMakeLists + cpuarch_ns
  • veneer / CMSE import library

Risks & buffer

High
Dual-core mailbox integration. Binding FSP inter-core comms to TF-M's tfm_hal_multi_core / platform_mailbox is the biggest unknown; no RA reference exists. Concentrated in P5.
High
RA8x2 core-topology is an open unknown. SPE vs NSPE core, and TZ-on-M85 + M33-as-NS vs pure multi-core, set the entire mailbox design — never examined. Needs an early spike (P4 start).
High
IAR replication. OFS / veneer / TZ placement + startup as IAR .icf; IAR TZ/veneer handling differs from GCC. Two rounds (RA6 P3, RA8x2 P6).
High
FSP 6.6 for RA8x2. First use for dual-core + SAU-reach-NS + RA8 support; regen churn and unverified dual-core generation.
Med
RA6 secure/NS integration. DDSC blocker solved (bsp_security.o compiles); remaining is wiring the regenerated RA6E1 secure/NS projects — crypto-stack includes, veneer, NS transition.
Med
New silicon. First RA8x2 bring-up — M85 PACBTI/FPU, RSIP, dual-core boot.
Med
Hardware. An EK-RA8x2 (dual-core) board must be procured before P4; 2× EK-RA6M4 bricked (RA6E1 is the RA6 vehicle).
Med
Shallow validation (accepted). Boot + a single crypto NSC path, not conformance. Stakeholders accepted this; psa-arch-tests remain a possible future addition beyond this plan.
Buffer. Dates are targets, not commitments — an overrun shifts subsequent dates rather than cutting scope. The RA8x2 leg (P4–P6) carries ~20–25% internal buffer and holds Dec 21 – Jan 2 as contingency. Everything is sequential under one engineer.
